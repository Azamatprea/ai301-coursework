# Rubric: is this plan ready to post and build from?

Every check reads the thing itself against the issue and its repro evidence, never the write-up's shape. A terse plan that is grounded, bounded, and testable passes; a long confident one that contradicts its own evidence, or wraps a small fix in a redesign, fails.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-grounded | The plan's stated cause (Diagnosis / Cause) read against the repro evidence: every step, output excerpt, and especially every control run or "ruled out" observation. See evidence-guide "Diagnosis and grounding". | Pass if the stated cause explains the behavior the repro evidence shows AND no observation in the repro evidence contradicts it (a control that behaves correctly with the suspected component still in the loop, a step showing the symptom already present before the suspected code runs, a run that isolates a different layer). Fail if any shown observation rules the cause out, if the plan adopts a thread member's confident diagnosis that the repro evidence does not support, or if it states no cause at all for a bug fix. A cause the plan labels as a hypothesis is fine only if the plan's first build step is the check that confirms it. | required |
| scope-bounded | The plan's in-scope statement, not-in-scope line, and approach steps, read against the single behavior the issue reports and the repro evidence isolates. See evidence-guide "Scope". | Pass if the plan is one bounded change that fixes the reported behavior: every approach step is needed for that fix or its regression test, and anything beyond it is explicitly left out (an honest deferral with a reason is fine, even when it narrows the fix). Fail if the approach adds anything the issue and repro do not require: a refactor, migration, new option or setting, dependency upgrade, UI rework, retry or abstraction framework, CI change, or a second fix for a different symptom. A fix wrapped in a redesign fails even when its core fix is right. | required |
| executable | The plan's files or areas, approach steps, and order of work. See evidence-guide "Executability". | Pass if a stranger could start the first step today without asking the author anything: the plan names the file(s), function(s), or the specific module or component the repro evidence points to, and the chosen approach is one concrete change, not a list of options. Naming a component and saying the exact function will be pinned while making that change is fine when the approach itself is already chosen. Fail if the plan defers a real decision to build time ("somewhere", "upstream or vendored, whichever is easier", "investigate X", "maybe also check Y", an unchosen layer or an unchosen approach) or names no files, components, or areas at all. | required |
| test-decisive | The plan's test plan read against the repro evidence's steps and artifacts. See evidence-guide "Test plan". | Pass if the test plan re-runs the repro (its steps, command, or input) against the change and names the observable outcome that must differ afterward (the exact output, value, exit code, or rendered state that the repro evidence showed wrong). Fail if the test plan is generic ("run the full test suite", "should feel fast", "nothing else should break") with no outcome tied to the reported behavior, or if it never re-runs the repro. | required |
| claims-honest | The plan and plan comment read against the repro evidence and the plan's own risks or unknowns. See evidence-guide "Honesty". | Pass if everything the plan or comment states as fact (cause, affected scope, that the change will fix the behavior) is shown by the repro evidence, and any open question the plan depends on is stated as an open question. A missing risks section is fine when nothing unknown is at stake. Fail if the plan or comment states as settled something the repro evidence does not show, or hides an unknown that the plan's own steps depend on. | required |
| thread-aware | The plan comment and plan read against the thread highlights (maintainer direction, named culprit, requested approach or test, linked prior-art PRs or branches). See evidence-guide "Comms". | Pass if the thread has no maintainer direction, or the plan follows that direction, engages the prior-art PR or branch it must coexist with, or says in its own words why it departs. Fail if an owner or maintainer in the thread has named a culprit, an approach, a requested test, or an open competing PR, and the plan or comment ignores it, contradicts it without saying so, or substitutes a different kind of change (for example a docs-only workaround where the maintainer has isolated a code fix). | required |
| ai-disclosure | The repo-facts block's contribution policy (AI section) read against the plan comment. Every package here is treated as AI-assisted work. See evidence-guide "Comms". | If the stated policy requires AI use to be disclosed in issues or comments (or "all AI usage in any form"), pass only if the comment says what tool was used and for what. If the policy requires comments to be human-written or in the contributor's own words, pass only if the comment reads as specific, personal words about this issue (not generic AI boilerplate). If the policy asks for disclosure only in pull requests, is permissive, or there is no AI policy, pass. Fail if a required disclosure is missing. | required |
| repo-conventions | The repo-facts block's contribution guide, templates, and review notes read against the plan and plan comment. | Pass if the plan respects the repo's stated conventions (tests expected, review-bandwidth notes, templates, CLA) or none are relevant. | preferred |

## Verdict rule

accept if every required check passes. Preferred checks never change the verdict. unclear on a required check counts as fail: a plan you cannot verify from the package is not ready to build from. The one exception: if the repro evidence block is absent or empty, cause-grounded and test-decisive are graded on what the plan itself quotes; if it quotes nothing, they are fail, not unclear.
