# Evidence guide: where evidence lives in a PR package

In an eval bundle the sections are: Repo facts, Issue, Thread highlights, Plan context (the accepted plan, with the repro evidence it built on), and Candidate PR (Title, Description, Commits, Diff, Test evidence). In live mode, the same parts live in the working copy and on GitHub: the repo's PR template (`.github/PULL_REQUEST_TEMPLATE.md`) and `docs/CONTRIBUTING.md` (repo facts), the issue body and thread, `plan.md` with its `## Deviations` heading (plan context), `git diff main...HEAD` plus `git log main..HEAD --oneline` (diff and commits), `pr_draft.md` (title on the first line, description below it), and `test_evidence.md` (test evidence). The package is what those hold, not other files in the working directory.

## Plan fidelity (harness category: silent-drift)

Where it lives: the plan states its scope in the "Plan" paragraph's "Scope" and "Not in scope" sentences, its "Files" list, and its approach steps (eval: the Plan context block; live: `plan.md`, "Scope", "Not in scope", "Files I will touch", "Approach"). Honest changes made during the build live in the plan's deviation notes (live: `plan.md`, `## Deviations`; eval: a "deviation note" sentence in the plan context or restated in the description). What the branch actually changed lives in the Diff (eval: the Candidate PR's Diff block; live: `git diff main...HEAD`, and `git diff main...HEAD --stat` for the file list). The description's claims about content live in the Description (eval) or `pr_draft.md`'s Summary and Changes sections (live).

What good looks like: every changed file and hunk is the plan's change, its test, a file the repo's stated template or guide requires for this kind of PR (a changelog entry, a translation string), or something a deviation note explains. A diff that does less than the plan is fine when the plan or description said so up front (a known limit, a deferral with its reason). Silent drift is any of these: a new flag, option, setting, rename, or rewrite the plan never listed (more than the plan); a planned fix, doc, or test missing from the diff with nothing disclosing it (less than the plan); a description that says "implements the plan exactly", "no changes beyond the fix", or "docs now document X" when the diff contradicts it or does not contain it. A deviation note re-ties a mismatch only if it was written in the plan; a deviation that exists only in the diff is drift.

## Test evidence (harness category: not-tested)

Where it lives: the Test evidence section (eval) or `test_evidence.md` with the Testing section of `pr_draft.md` (live). Read it against the plan's test plan and expected-after (eval: the plan context's "Test plan" sentence and the repro evidence; live: `plan.md`, "Test plan", and the unit-2 repro). The repo's own check commands live in the repo facts (eval) or the PR template's Testing checklist and `docs/CONTRIBUTING.md` (live: `make test-unit`, `make test-integration`, `make lint`, `make typecheck`).

What good looks like: the plan's own repro (its command, input, or flow) is shown running on the change, with an exact observable that differs from the "before" (an output, a value, an exit code, a screen state) and that matches the plan's expected-after; every control the plan promised is shown too; and the outcome of the repo's own check command is visible. Decisive evidence names the observable and the before and after. Not decisive: "tested locally", "works on my machine", "all tests pass" with no output and no named test; a run of a neighbor of the repro (a different input, a control only, the path the fix did not change); one run when the plan named two failure modes; or a pasted output that does not match the expected-after. A failing or non-running check that is pasted and explained (for example `make test-integration` stopping with "no tests ran" because the repo has none) is honest evidence, not a failure.

## Diff quality (harness category: unreviewable)

Where it lives: the unified Diff and the Commits list (eval: the Candidate PR's Diff and Commits blocks; live: `git diff main...HEAD` and `git log main..HEAD --oneline`). Read every added line (`+` lines), plus whole hunks that appear to change only whitespace or order.

What good looks like: the fix is visible and small; every added line belongs to the fix, its test, or a repo-required entry. The debris tells are: debug leftovers (`print`, `eprintln!`, `console.log`, `DEBUG` logging), commented-out code (including a commented-out first attempt), a dead function or import that nothing uses (often under an `allow(dead_code)` or `_unused` name), a TODO or FIXME the diff adds, formatting or re-indentation churn, reordered imports, hunks that reprint identical lines, and drive-by edits to unrelated files or help text. Commit messages such as "wip", "misc cleanups while debugging", or "fmt + cleanup" point to where to look. One genuine explanatory comment about the fix is not debris. In live mode, also read the changed-file list: it should list only files the fix changes, and never `plan.md`, `comment.md`, `pr_draft.md`, or `test_evidence.md`.

## Standards and comms (harness category: standards-wall)

Where it lives: the repo's stated asks live in the repo facts' "pull requests:" and "contribution policy" lines (eval) or in `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md` (live: Summary, Issue with `Closes #`, Changes, Testing checklist, Screenshots / Demo, Notes for Reviewers; branch naming `<type>/<issue-number>-<short-description>`; conventional-commit messages; the xfail-marker rule for seeded bugs). The PR's honoring of them lives in the Description (eval) or `pr_draft.md` (live), and, for artifacts the repo asks for, in the Diff (a changelog or whatsnew entry, a translation string, a test file). The AI policy is stated in the repo facts' contribution policy line (eval) or in `docs/CONTRIBUTING.md` and the template's Notes for Reviewers ask (live; scope.md adds that the course always asks for it).

What good looks like: every required template section is filled with content specific to this change (a closing line with the real issue number, a Changes list matching the diff, a Testing section with ticked boxes that the evidence supports and unticked boxes explained); every artifact the repo asks for is actually in the diff, not just promised; maintainer direction in the thread is followed or explicitly departed from; and if the policy requires AI disclosure, the description names the tool and what it did, in the author's own words when the policy requires that. Boilerplate that fits any PR ("see diff", an empty checklist, a Summary of one word) does not count, and neither does a ticked box the evidence contradicts. Whether the description's claims match the diff is plan fidelity, above, not this section.
