# Rubric: is this pull request ready to submit?

Every check reads the artifact itself (the diff, the evidence, the description) against the plan, the issue, and the repo's stated asks. It never reads the write-up's shape. A terse PR that stays inside its plan, proves the fix, carries no debris, and meets the repo's asks is ready. A polished, confident PR that does more or less than its plan, proves nothing observable, buries the fix, or ignores the repo's template fails. A PR that honestly says what it does not do, with a diff that matches, is not a failing PR.

The four ways a PR gets held, and the checks that catch them: silent drift (`diff-in-plan`, `claims-match-diff`), not tested (`repro-rerun-decisive`, `repo-checks-shown`), unreviewable (`diff-reviewable`), standards wall (`template-honored`, `ai-disclosed`).

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-in-plan | The diff's changed files and hunks (`git diff main...HEAD`, or the bundle's Diff block) read against the plan's named files, its in-scope and not-in-scope lines, its approach steps, and its deviation notes. See evidence-guide "Plan fidelity". | Pass if every changed file and every hunk is the plan's change, a test for it, a file the repo's stated PR template or contributing guide requires for this kind of change (a changelog or whatsnew entry, a translation string, regenerated docs), or something a deviation note in the plan explains. Pass also if the diff does LESS than the plan and the plan or the description says so in advance (an honest deferral). Fail if the diff contains a new option, flag, setting, rename, rewrite, refactor, or behavior the plan did not list and no deviation note covers, or if the diff skips a planned deliverable (a planned fix, doc, or test) and nothing discloses it. | required |
| claims-match-diff | Every sentence in the PR title and description that claims what the change contains ("implements the plan exactly", "no changes beyond the fix", "docs now document X", "adds tests for Y"), each read against the diff. See evidence-guide "Plan fidelity". | Pass if every claim of content or coverage is true of the diff, and every stated limitation matches what the diff leaves out. Fail if the description claims something the diff does not contain (a doc update, a test, a case handled), or claims fidelity or "nothing else changed" while the diff contains changes outside the plan. A description that says less than the diff does about a plan-covered change is fine; a description that says more than the diff does is not. | required |
| repro-rerun-decisive | The test evidence read against the plan's test plan and the reproduction it builds on (the issue's repro command, input, or flow). See evidence-guide "Test evidence". | Pass if the evidence re-runs the plan's repro (its command, input, or flow, not a neighbor of it) on the change, names the observable that changed (an exact output, value, exit code, or screen state), and the observable matches the plan's expected-after. Controls the plan names must be re-run too if the plan promised them. Fail if the evidence is only a bare claim ("tested locally", "works on my machine", "tests pass") with no output or named test, if it exercises the path the fix did not change (a different input, a control only), if the plan named two failure modes or two repro cases and only one is re-run, or if the shown output does not match the expected-after. | required |
| repo-checks-shown | The test evidence read against the commands the repo's PR template, contributing guide, or the plan name for checking a change (test suite, linter, type checker). See evidence-guide "Test evidence". | Pass if the evidence shows the outcome of the repo's own test or check command for this change (the command and its result, or a named test that exercises the fix and passes), and any command that failed or could not run is reported with the reason. A failing check reported honestly with its reason passes this check. Fail if the repo's checks were never run and nothing says why, or the evidence shows or hides a failure the description does not mention. | required |
| diff-reviewable | The diff and the commit list, read for leftovers: debug prints, commented-out code, dead functions or imports, TODO notes the change adds, formatting or whitespace churn, reordered imports, and hunks in files unrelated to the fix. See evidence-guide "Diff quality". | Pass if every added line is part of the fix, its test, or a repo-required entry, and the diff contains no debug output, no commented-out code, no dead code kept "for later", no formatting or import churn on lines the fix does not need, and no drive-by edit. Fail if any such debris appears in the diff, even when the core fix is right and well evidenced. Commit messages like "wip" or "misc cleanups while debugging" are a tell to read the diff harder, not a fail on their own. | required |
| template-honored | The repo-facts block's PR template asks and contributing-guide asks (eval), or `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md` (live), read against the description and the diff. See evidence-guide "Standards and comms". | Pass if every section or checklist item the repo states as required is present with real content for this change, and every artifact it asks for (an issue-closing line such as `Closes #N`, a changelog or whatsnew entry, a translation string, a test) is actually present in the description or in the diff. A box may stay unticked only if the description says why. If the repo has no template, pass if the description references the issue and the contributing guide's stated asks are met. Fail if a required section is empty, boilerplate, or deleted, if the closing line is missing, if a ticked box is contradicted by the evidence, or if a stated ask (a changelog entry, a CLA note) is visibly ignored. | required |
| ai-disclosed | The repo-facts block's AI policy (eval), or `docs/CONTRIBUTING.md`, the PR template's Notes for Reviewers, and the course rule in scope.md (live), read against the description. Treat every package as AI-assisted work. See evidence-guide "Standards and comms". | If the repo's stated policy requires AI use to be disclosed (any wording like "all AI usage must be disclosed", "state the tool and extent"), pass only if the description names the tool and what it did. If the policy requires human-written or own-words text, pass only if the description carries an AI statement and reads as specific to this change. In live mode on Path Review, the template asks for the student's own words on how AI was used: pass if the Notes for Reviewers section names the tool and what it was used for. If the policy is permissive, asks for disclosure only elsewhere, or there is no stated AI policy, pass. Fail if a required disclosure is absent. | required |
| commits-and-title | The PR title and commit messages read against the repo's stated conventions (conventional-commit title, a scope, a branch name with type prefix and issue number). | Pass if the title says what the change does in the repo's stated style, and each commit message follows the stated convention. | preferred |

## Verdict rule

Accept if every required check is `pass`. Reject if any required check is `fail`. `unclear` on a required check counts as `fail`: a PR that cannot be verified from the package is not ready to submit. The preferred check is graded and reported but never changes the verdict. The grades of checks do not influence each other: a PR that fails `diff-reviewable` can still pass `repro-rerun-decisive`, and the verdict still turns on the failing one.

A disclosed shortfall is not a failure: if the plan or the description states what the PR deliberately leaves out, and the diff leaves out exactly that, `diff-in-plan` and `claims-match-diff` both pass, and a clean, well-evidenced PR with such a disclosure is accepted.
